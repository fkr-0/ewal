* Overview

=ewal= is a pywal-compatible, terminal-aware color and theme toolkit for Emacs.
It turns a small palette into reusable semantic colors, contrast-safe editor
faces, Doom and Spacemacs themes, Evil cursor styles, and palette inspection
workflows.

The core remains dependency-light and works in batch Emacs. Optional integration
packages add Doom themes, Spacemacs themes, Evil cursor and mode-line styling,
dynamic theme generation, palette auditing, and Transient interfaces.

This repository is the maintained =fkr-0/ewal= fork. The original project remains
recorded as the Git =upstream= remote, while this fork carries the contrast,
testing, documentation, and release work described in [[./CHANGELOG.md][CHANGELOG.md]].

* Highlights

- Reads traditional pywal JSON and compatible colrz output.
- Includes 256 bundled dark and light palettes.
- Parses hexadecimal colors without relying on the active terminal or display.
- Implements WCAG relative luminance and contrast calculations.
- Repairs weak or identical foreground/background pairs deterministically.
- Derives stable semantic roles for foreground, comment, cursor, and highlight.
- Generates and audits Doom and Spacemacs themes.
- Styles Evil cursors and optional state-aware mode-lines.
- Audits complete palette directories in interactive or batch workflows.
- Keeps optional user interfaces separate from batch-safe libraries.
- Ships ERT tests, warnings-as-errors compilation, linting, and GitHub Actions.

* Installation

** Source checkout

Clone the maintained fork and place the required package directories on
=load-path=:

#+begin_src sh
git clone https://github.com/fkr-0/ewal.git ~/src/ewal
#+end_src

#+begin_src emacs-lisp
(add-to-list 'load-path "~/src/ewal")
(add-to-list 'load-path "~/src/ewal/doom-themes")
(add-to-list 'load-path "~/src/ewal/spacemacs-themes")
(add-to-list 'load-path "~/src/ewal/evil-cursors")
(require 'ewal)
#+end_src

Only add the optional subdirectories that are actually used.

** package-vc

On Emacs versions with =package-vc-install=, the core package can be installed
from the maintained repository:

#+begin_src emacs-lisp
(package-vc-install "https://github.com/fkr-0/ewal")
(require 'ewal)
#+end_src

Optional integration packages remain separate package boundaries in the same
repository. Their dependencies must be installed before loading them.

** Existing package archives

The upstream project has historically published =ewal=,
=ewal-spacemacs-themes=, and =ewal-evil-cursors= as separate packages. Archive
versions can therefore differ from this fork's current release. Use the source
checkout when exact =v0.3.2= behavior is required.

* Quick start

#+begin_src emacs-lisp
(require 'ewal)

;; Loading is lazy, but an explicit load is useful when inspecting state.
(ewal-load-colors)

;; Retrieve semantic or ANSI-like roles.
(ewal-get-color 'foreground)
(ewal-get-color 'magenta)

;; Positive shades lighten; negative shades darken.
(ewal-get-color 'magenta 4)
(ewal-get-color 'background -2)
#+end_src

* Palette source precedence

When =ewal-load-colors= is called, Ewal resolves palette sources in this order:

1. An explicit JSON file passed to =ewal-load-colors=.
2. =ewal-json-file=, which defaults to the traditional
   =~/.cache/wal/colors.json=.
3. The first existing file in =ewal-json-file-fallbacks=, which defaults to
   =~/.cache/colrz/current/colors.json=.
4. The configured bundled palette when no external file exists or
   =ewal-use-built-in-always= is non-nil.

This keeps pywal compatibility while making the fork work directly with colrz.
The selected source is cached and reloaded when its identity or modification
time changes. Pass a non-nil FORCE argument to reload unconditionally.

External JSON is validated before it can replace the active palette. A valid
cache contains =special= and =colors= sections, valid background and foreground
colors, and at least one ANSI =colorN= entry. Cursor and the remaining ANSI
slots may be omitted and are derived or left unavailable as appropriate.

Ewal compares file metadata before and after reading. If a palette producer
rewrites or atomically replaces the cache mid-read, Ewal retries the complete
read. Stable malformed or incomplete input falls back to the configured
built-in palette. Cached source identity includes modification and status-change
times, size, inode, and device metadata so timestamp-preserving replacement is
detected. The retry count is configurable:

#+begin_src emacs-lisp
(setq ewal-json-read-retries 2)
#+end_src

#+begin_src emacs-lisp
;; Add another compatible producer without replacing pywal precedence.
(add-to-list 'ewal-json-file-fallbacks
             "~/.cache/my-palette/colors.json" t)

;; Force a refresh after changing source settings.
(ewal-load-colors nil t)
#+end_src

** Use bundled palettes

#+begin_src emacs-lisp
(setq ewal-use-built-in-always t
      ewal-dark-palette-p t
      ewal-built-in-palette "sexy-material")
(ewal-load-colors nil t)
#+end_src

Bundled palettes are resolved relative to the installed library. Ewal does not
assume a particular =~/.emacs.d= layout.

To use another palette tree:

#+begin_src emacs-lisp
(setq ewal-built-in-palette-path "~/path/to/palettes/")
#+end_src

* Contrast policy

The loader normalizes colors and derives missing semantic roles before adaptors
construct faces. Default thresholds are:

- ordinary text, including comments: =4.5:1=
- cursors, highlights, and non-text UI boundaries: =3.0:1=

#+begin_src emacs-lisp
(setq ewal-color-minimum-text-contrast 4.5
      ewal-color-minimum-ui-contrast 3.0)
#+end_src

Contrast uses the WCAG sRGB linearization formula. Hexadecimal colors are
parsed directly, so batch jobs and daemon startup do not depend on terminal
color tables. When a color misses its target, Ewal first considers palette
colors and then deterministic light/dark alternatives.

* Integrations

** Doom themes

#+begin_src emacs-lisp
(require 'ewal-doom-themes)
(require 'ewal-generate-doom-theme)

(setq ewal-doom-themes-min-contrast 4.5
      ewal-doom-themes-min-ui-contrast 3.0
      ewal-doom-themes-preview-limit 8)

;; Generate a Doom theme from a palette JSON file.
(ewal-generate-doom-theme-interactive)

;; Audit the active Doom theme.
(ewal-doom-themes-check-contrast)
#+end_src

Shipped theme entrypoints include:

- =ewal-doom-one=
- =ewal-doom-outrun-electric=
- =ewal-doom-tokyo-night=
- =ewal-doom-vibrant=

The adaptor resolves semantic roles before theme construction and repairs
foreground/background collisions instead of emitting them unchanged.

** Spacemacs themes

#+begin_src emacs-lisp
(require 'ewal-spacemacs-themes)

(setq ewal-spacemacs-themes-min-contrast 4.5
      ewal-spacemacs-themes-min-ui-contrast 3.0)

(load-theme 'ewal-spacemacs-modern t)
#+end_src

Available entrypoints are =ewal-spacemacs-classic= and
=ewal-spacemacs-modern=. Text and UI roles are checked separately, and each role
is compared with the background on which it is actually rendered.

** Evil cursors and mode-lines

#+begin_src emacs-lisp
(require 'ewal-evil-cursors)

(setq ewal-evil-cursors-obey-evil-p t)
(ewal-evil-cursors-get-colors :apply t)

;; Include Spacemacs cursor integration when available.
(ewal-evil-cursors-get-colors :apply t :spacemacs t)
#+end_src

Cursor backgrounds are checked against the editor background. Text-bearing
mode-line faces receive a foreground that meets the text threshold.

** Theme contrast inspection

#+begin_src emacs-lisp
(require 'ewal-theme-contrast-check)

;; Report the current theme.
(ewal-check-current-theme-contrast)

;; Preview or apply palette-based suggestions.
(setq ewal-contrast-suggestion-strategy 'palette)
(ewal-contrast-preview-suggestions)

;; Optional Transient workflow.
(ewal-check-contrast-panel)
#+end_src

Applied suggestions can be retained as inspectable theme/face override data and
exported as a =use-package= snippet. Ewal never edits user configuration files
silently.

** Palette audits

Interactive report:

#+begin_src emacs-lisp
(require 'ewal-palette-utils)
(ewal-audit-palettes-contrast "~/path/to/palettes" 4.5)
#+end_src

Batch report:

#+begin_src sh
emacs --batch -Q -L /path/to/ewal \
  --eval "(progn (require 'ewal-palette-utils) \
          (ewal-audit-palettes-contrast-batch \"/path/to/palettes\" 4.5))"
#+end_src

Optional palette browser:

#+begin_src emacs-lisp
(ewal-palettes-transient)
#+end_src

* Development

The repository uses [[https://github.com/emacs-eldev/eldev][Eldev]] to isolate development dependencies and to run the
same checks locally and in CI.

#+begin_src sh
eldev test
eldev compile --warnings-as-errors
eldev lint
eldev exec --dont-require --file scripts/package-lint.el
sh scripts/package-smoke.sh
#+end_src

The consolidated release gate is also exposed through =bridge.yml= as =check=:

#+begin_src sh
eldev test && eldev compile --warnings-as-errors && eldev lint && \
  eldev exec --dont-require --file scripts/package-lint.el && \
  sh scripts/package-smoke.sh
#+end_src

The test suite covers:

- WCAG reference values and headless hexadecimal parsing
- pywal-primary and colrz-fallback source resolution
- semantic role derivation and contrast repair
- all bundled JSON palettes
- Doom and Spacemacs adaptor thresholds
- Evil cursor and mode-line behavior
- dynamic Doom theme generation
- runtime loading and stable theme names
- contrast reports, suggestions, overlays, and persistent overrides
- release metadata, package dependency versions, and removed migration stubs
- immutable CI action references and package-boundary metadata

Declarative theme entrypoints use =no-byte-compile: t= because their macros
produce source forms that are not useful as ordinary byte-compiled libraries.
Reusable libraries and adaptors compile with warnings treated as errors.

The repository contains several package boundaries. A single repository-wide
=package-lint= pass interprets every file relative to =ewal.el= and therefore
reports misleading dependency errors for the optional packages. Checkdoc and
Relint run repository-wide; package-lint belongs in a package-specific matrix,
which is tracked in [[./ROADMAP.md][ROADMAP.md]].

* Continuous integration

[[./.github/workflows/ci.yml][GitHub Actions CI]] runs the following gate for Emacs 28.1, 29.4, and 30.2:

1. ERT tests through Eldev.
2. Byte compilation with warnings treated as errors.
3. Checkdoc and Relint.
4. Independent package-lint checks for every published package entrypoint.
5. Package tarball construction and installed built-in-palette smoke testing.

The core still declares Emacs 25.1 compatibility. The hosted integration matrix
starts at 28.1 because the current Transient development dependency requires
Emacs 28.1. Reproducibly exercising the core minimum without optional package
constraints remains an explicit roadmap item.

* Releases and versioning

Repository releases follow Semantic Versioning and use annotated =vMAJOR.MINOR.PATCH=
Git tags. The canonical version is recorded in [[./VERSION][VERSION]], mirrored by the
=ewal.el= package header and =ewal-version=, and protected by ERT tests.

Before tagging a release:

1. Update =VERSION= and package headers.
2. Move user-visible changes from =Unreleased= into a dated section in
   [[./CHANGELOG.md][CHANGELOG.md]].
3. Run the complete Eldev gate.
4. Review the Git diff and release evidence.
5. Create the annotated tag only after all mandatory checks pass.

* Fork lineage and contributions

The Git remote convention is:

- =origin=: maintained fork at =fkr-0/ewal=
- =upstream=: original project at =cyruseuros/ewal=

Changes should preserve compatibility where practical, keep optional dependencies
outside the core, include focused tests, and document behavior that affects
palette precedence, contrast policy, package boundaries, or public functions.
